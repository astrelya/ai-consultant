# Story 5.10: Default Logging Scaffold in Generated Projects

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a user,
I want every project generated by ai-consultant to include a working structured logger from the very first ticket,
so that I can trace errors in the output codebase without adding logging myself (FR-21 / Epic 5).

## Acceptance Criteria

1. **Given** `SupervisorAgent._execute_ticket(project_id, ticket_id, ticket_ids)` is invoked
   **When** the loaded `project` and the current `ticket_ids` queue satisfy `is_first_ticket(project, ticket_ids, ticket_id) == True`
   **Then** the supervisor MUST call a new pure static helper `SupervisorAgent._build_logging_scaffold_instruction(story_details)` BEFORE `story_details["description"]` is finalised for delegation (specifically: AFTER the Story 5.3 `_build_accumulated_context` block is prepended to `description`, and BEFORE `_delegate_to_developer` is called), and MUST prepend the returned string to `story_details["description"]` using the exact separator `"\n\n"`. The helper is pure Python — no LLM call, no DB call, no I/O — so this injection MUST NOT add any billable token round-trip beyond the single existing ticket-implementation call (FR-21, AD-4).

2. **And** `is_first_ticket` is a new pure static helper on `SupervisorAgent` with the signature `@staticmethod def _is_first_ticket(project: dict, ticket_ids: Sequence[str], current_ticket_id: str) -> bool`, positioned IMMEDIATELY BELOW `_find_ticket` and ABOVE `_build_accumulated_context` (keeps queue-inspection helpers grouped). It MUST return `True` if AND ONLY IF BOTH of the following hold:
   - `current_ticket_id == ticket_ids[0]` when `ticket_ids` is non-empty (positional first in the current execution queue), AND
   - No ticket in `project.get("ticket_history") or []` has `status` in the set `{"Done", "In Review"}` (no ticket has ever been successfully closed in this project's persistent history — Story 5.4 cross-session memory guarantees this survives restarts).

   All other cases return `False`. Empty `ticket_ids` returns `False`. A missing or non-list `ticket_history` is treated as empty. This definition means: (a) if the very first ticket errors out and the user re-runs, the scaffold instruction is still injected on the retry; (b) if any later ticket in the queue becomes the "first" (e.g. deselection in Story 4.4), the scaffold is still injected as long as no ticket has previously reached Done/In Review; (c) once one ticket has been closed, no future ticket in that project ever gets the scaffold instruction again.

3. **And** `_build_logging_scaffold_instruction(story_details)` MUST return a single string with EXACTLY this shape (verbatim — the test in Task 4.2 asserts the block by substring match on the fenced headers and each labelled bullet):
   ```
   --- Logging scaffold requirement (FR-21) ---
   This is the FIRST ticket implemented in a newly generated project. In addition to the ticket's own acceptance criteria, the generated codebase MUST include a working structured logging scaffold. All subsequent tickets will import and reuse this scaffold — do NOT postpone it.

   Required elements:
   - Structured logging setup: configure Python's standard `logging` module (or the target stack's idiomatic equivalent if the project is not Python) at level `INFO` by default. Use `logging.basicConfig(level=..., format="%(asctime)s %(levelname)s %(name)s: %(message)s")` or an equivalent framework-native configuration. Do NOT use `print()` as the diagnostic surface.
   - Reusable module logger: expose a module-level logger via `logger = logging.getLogger(__name__)` in each generated source module. The scaffold module itself MUST be importable by every subsequently generated module without requiring extra setup calls at import time (no `configure_logging()` call must be forced on downstream modules).
   - Env-var-driven level: read the log level from environment variable `LOG_LEVEL` with default `"INFO"`. Use `logging.getLevelName(os.environ.get("LOG_LEVEL", "INFO").upper())` (or the target-stack equivalent) so `LOG_LEVEL=DEBUG`, `WARNING`, etc. all work. Invalid values MUST fall back to `INFO` — never raise at import time.
   - Passing pytest test: add a test file at `tests/test_logging.py` (or the project's existing test directory if one exists) containing at minimum a test named `test_logger_initializes_without_error` that (a) imports the logging scaffold module, (b) asserts `logging.getLogger("<scaffold_module_name>")` returns a `logging.Logger` instance, and (c) asserts the configured level matches the default (`logging.INFO`) when `LOG_LEVEL` is unset. The test MUST pass under `pytest` with zero warnings introduced by the scaffold itself.
   - No hard-coded credentials, no external log sinks (no Sentry, Datadog, cloud logging clients) — stdout/stderr only. Any transport upgrade is a future ticket.
   - Idempotency: if a logging scaffold already exists in the target repo (a module already defines `logging.basicConfig` at import time, OR a file named `logging_config.py` / `logger.py` already lives at the repo root or `src/`), you MUST reuse and extend it rather than creating a parallel scaffold. Detection is best-effort file-existence + string-scan; on ambiguity, prefer reuse.
   --------------------------------------------
   ```
   The block MUST end with the closing dashed footer line `--------------------------------------------` and MUST NOT include a trailing newline (the caller supplies `"\n\n"` between this block and the rest of `description`). No `<...>` placeholders remain in the returned string — the block is a static template. `story_details` is passed for future extensibility (e.g. per-project language override) but is NOT consulted in this story's implementation — the helper returns the same block regardless of input. Tests in Task 4.2 assert the header line, footer line, and the exact bullet labels: `Structured logging setup:`, `Reusable module logger:`, `Env-var-driven level:`, `Passing pytest test:`, `Idempotency:`.

4. **And** the injection order inside `_execute_ticket` MUST be, in this precise sequence (existing steps preserved verbatim except where noted):
   1. `story_details` dict is built from the ticket record (existing lines 111–117).
   2. `accumulated_context = self._build_accumulated_context(project, ticket_ids, ticket_id)` (existing line 120).
   3. **NEW:** `scaffold_instruction = self._build_logging_scaffold_instruction(story_details) if self._is_first_ticket(project, ticket_ids, ticket_id) else ""`.
   4. `story_details["accumulated_context"] = accumulated_context` (existing).
   5. **NEW:** `story_details["logging_scaffold_instruction"] = scaffold_instruction` (empty string when not first ticket — the key is ALWAYS set for uniform downstream consumption).
   6. Description composition (REPLACES existing lines 124–127):
      ```python
      description_parts = [
          part
          for part in (scaffold_instruction, accumulated_context, story_details["description"])
          if part
      ]
      story_details["description"] = "\n\n".join(description_parts)
      ```
      Order matters: scaffold instruction FIRST (highest priority — appears at the top of the developer's prompt), then accumulated context, then the ticket's own description. When both scaffold_instruction and accumulated_context are empty, the description is unchanged.

5. **And** the returned dict from `_execute_ticket` on ALL paths (success, error, blocked) MUST NOT expose `logging_scaffold_instruction` at the top level — it lives only on `story_details` where the developer agent reads it. No SSE event type is added or extended by this story. No new `agent_log` message is REQUIRED; however, when the scaffold instruction is injected the supervisor SHOULD publish a single informational `agent_log` event `{"message": f"[Supervisor] Injecting default logging scaffold instruction for first ticket {ticket_id} (FR-21)."}` positioned IMMEDIATELY BEFORE the existing `"Preparing environment for ticket …"` event so that the user sees FR-21 in action. This log message is asserted verbatim by the test in Task 4.3.

6. **And** the ticket state machine is UNCHANGED. `Pending → In Progress → Done | Error | Agent Blocked` (spine §"Ticket state machine") is not touched by this story. The scaffold instruction rides inside the ticket-implementation LLM call — it does not introduce a new ticket status, a new SSE event type, or a new gate before delegation. If the developer agent fails to produce the scaffold, that failure surfaces via the EXISTING `TesterAgent` flow (Story 5.6 gate) or the EXISTING Story 5.7 regression-fix flow — Story 5.10 does not add a scaffold-specific verification step in the supervisor.

7. **And** the developer agents (`LocalDeveloperAgent.implement_feature` and `RemoteDeveloperAgent.implement_feature`) MUST NOT be modified. The scaffold instruction reaches them through `story_details["description"]` (which both agents already interpolate into their existing `system_prompt` under the same `{description}` slot — verified in `agents/local_developer_agent.py` line 76 and `agents/developer_agent.py` line 45). Both agents already have Context7 grounding (AD-8) and MCP tool access sufficient to write the scaffold module and the pytest test. This story adds ZERO new imports, ZERO new tool functions, and ZERO new prompt-composition logic inside the developer modules — the extension point is `story_details["description"]` only.

8. **And** `SupervisorAgent._build_accumulated_context` MUST NOT be modified. The scaffold instruction is injected in a separate step (AC-4 step 3/6) and lives adjacent to but not inside the accumulated-context builder. This keeps Story 5.3's contract intact and lets the first-ticket case (empty accumulated_context by definition — no prior tickets in the queue precede position 0) not conflict with the new injection.

9. **And** if `story_details["description"]` is already empty (defensive edge case — the ticket record has no description), the scaffold instruction still injects successfully and becomes the entire description: `"\n\n".join(["<scaffold_block>"])` equals the scaffold block itself, with no leading or trailing blank lines. A test asserts this via a synthetic ticket with `"description": ""`.

10. **And** the FR-21 test artefact for THIS story (Story 5.10) is the pytest suite added under `tests/` per Task 4 — NOT a scaffold file inside a generated project. The AC's promise "a pytest test confirms the logger initializes without errors on import" is fulfilled at TWO levels:
    - **This story's tests** (`tests/test_supervisor_logging_scaffold.py`) verify the supervisor correctly injects the instruction and its shape (unit-level).
    - **The instruction itself** (AC-3) mandates that the DEVELOPER agent generates a `tests/test_logging.py` inside every new project. Verification that the developer actually complies is out of scope for this story — that verification is the responsibility of TesterAgent (Story 5.6 test-artifact gate) on the first ticket. No mock of that behaviour is required here.

    ```python
    @staticmethod
    def _is_first_ticket(
        project: dict, ticket_ids: Sequence[str], current_ticket_id: str
    ) -> bool:
        """FR-21: True iff this is the first ever ticket in the project.

        Positional (queue[0]) AND persistent (no prior Done/In Review in
        ``project.ticket_history``). Cross-session safe: on a re-run after a
        failed first ticket, this still returns True until at least one
        ticket has been closed successfully.
        """
        ticket_list = list(ticket_ids)
        if not ticket_list or ticket_list[0] != current_ticket_id:
            return False
        history = project.get("ticket_history") or []
        if not isinstance(history, list):
            return False
        closed = {"Done", "In Review"}
        for t in history:
            if isinstance(t, dict) and t.get("status") in closed:
                return False
        return True
    ```

### Why the injection lives on the supervisor (not the developer)

The scaffold requirement is a project-lifecycle policy (FR-21: "every project generated by ai-consultant"), not a language-specific code recipe. Placing it on the supervisor centralises the first-ticket detection (`_is_first_ticket`) alongside the existing cross-ticket context builder (`_build_accumulated_context`) — both are queue-position + history-position queries. The developer agents remain stateless per-invocation and language-agnostic. This mirrors the AD-4 principle ("LLM-as-last-resort": the LLM never determines whether it's the first ticket — the supervisor computes that deterministically from project state).

### Why the block is a static template

FR-21 doesn't specify a target stack — projects can be Python, Node, Go, etc. The scaffold block is written to be Python-primary (matches the ai-consultant repo's own stack per project-context.md) but includes the explicit escape hatch "or the target stack's idiomatic equivalent if the project is not Python" so the developer agent can adapt when the ticket describes, e.g., a Node project. Per-project language detection is a future extension — the `story_details` parameter is reserved on the helper signature for that.

### Idempotency detection is intentionally best-effort

The scaffold instruction (AC-3) tells the developer to reuse existing logger scaffolds when detected. Detection is file-existence + string-scan — no AST parsing, no import graph traversal. This is the same pragmatic level of static analysis used elsewhere in the agent flow (e.g. Story 5.8's diagnostic-logging heuristic). If the developer creates a duplicate scaffold, the resulting test failure surfaces via Story 5.6's gate — not via a supervisor-side enforcement.

### Why we don't emit a new SSE event type

The AC-5 `agent_log` message reuses the existing `agent_log` event type. Introducing a new event type (e.g. `scaffold_injection`) would require a frontend Chat View handler (Story 2.3) and a corresponding frontend test. All the user needs to see is a plain diagnostic message — the existing `agent_log` handler already renders it. This matches AD-7 (streaming over polling) and AD-10 (REST + SSE only) without adding a new discovery surface.

### Why `_prior_attempts` (Story 5.9 AC-6) is unaffected

Story 5.9's `_prior_attempts` key rides on `dev_result` (the developer's return dict) — it exists only during regression escalation. Story 5.10's `logging_scaffold_instruction` rides on `story_details` (the input dict to the developer) — it exists only during ticket preparation. Disjoint namespaces, disjoint lifecycles. No key collision.
