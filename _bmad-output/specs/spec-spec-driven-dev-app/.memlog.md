- (decision) Why: solo developers and team contributors want to delegate implementation to a coordinated AI agent team while retaining PM-level control; current agents are stateless, blind, and isolated making them untrustworthy for multi-ticket projects
- (capability) CAP-1: spec-to-ticket pipeline — user provides spec, engages clarifying dialogue, system outputs structured user stories and Jira tickets; success: given a spec, the system produces a complete, PM-reviewable ticket set with project name embedded in ticket titles
- (capability) CAP-2: sequential ticket execution with shared memory — agents implement tickets one at a time, each with access to accumulated codebase context and prior outcomes; success: no ticket is implemented without prior ticket context; no merge conflicts from parallel execution
- (capability) CAP-3: live agent thought log — real-time activity stream visible in UI during execution, no silent gaps; success: user can see every reasoning step as it happens; no 3-minute silences ending with bare 'success'
- (capability) CAP-4: persistent cross-ticket and cross-session memory — project config, codebase context, decisions, and ticket history accumulate and are shared across agents and sessions; success: second session starts with full project knowledge; no information re-requested that was given in a prior session
- (capability) CAP-5: confidence-threshold exception model — agents declare confidence before acting; below threshold they pause and surface a structured exception with user intervention point; user can inspect and modify before ticket closes; success: no agent proceeds blindly below threshold; every exception is human-actionable
- (capability) CAP-6: mandatory test-verified ticket closure — no ticket marked complete without actual test execution and a verifiable artifact; success: ghost validation (reporting success without running tests) is a hard system failure; every closed ticket has a linked test artifact
- (capability) CAP-7: PM-style dashboard interface — lightweight IDE-like UI with visible codebase view, live activity stream, progressive disclosure (summary default, drill-down on demand), and PM controls (approve, reject, intervene, re-run); success: non-technical PM can operate full workflow without CLI or code knowledge
- (capability) CAP-8: Context7-grounded code generation — all code generation actively grounded against current library and framework docs; success: no hallucinated APIs or outdated patterns in generated code
- (constraint) Tickets must execute sequentially, never in parallel — prevents merge conflicts and context isolation failures
- (constraint) No ticket may be marked complete without actual test execution and a verifiable artifact — ghost validation is a hard failure
- (constraint) Project configuration is captured once and must persist for the lifetime of the project — never re-requested
- (constraint) Interface must be operable without technical depth — complexity is opt-in
- (constraint) All code generation must be grounded via Context7 against current library/framework docs
- (constraint) No silent agent failures — every blocked or low-confidence state is surfaced explicitly to the user
- (decision) Non-goals: parallel ticket execution; full zero-interaction autonomy; stateless per-session agents; information-overload UI (surfacing everything at once); ghost validation; re-asking for already-provided project config
- (decision) Success signal: solo dev provides spec, steps away, agent team implements and tests tickets sequentially with live thought logs, user intervenes only on exception, ends with committed test-verified implementation
- (assumption) Jira is the primary ticket-management integration target based on explicit Jira mention in source
- (assumption) Python + LangGraph is the implementation stack based on project-context.md
- (question) What is the right intervention model — approve each ticket before execution, after, or only on exception?
- (question) How is the codebase view scoped — full repo browser, or files touched by the current ticket only?
- (question) Jira integration handoff: does the app write tickets to Jira, consume from an existing backlog, or both?
- (question) How is the confidence threshold calibrated — per agent, per ticket type, user-configurable, or global?
- (question) Is there a regression gate — what happens when new code passes tests but breaks existing functionality?
